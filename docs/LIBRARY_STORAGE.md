# Local library storage — SQLite

The current storage backend is SQLite, replacing the published JSON writer. The current catalog persists stable track IDs/paths plus title, artist, album, duration and metadata-inspection state. It also persists flat crates and track membership; constant-BPM beatgrids are also stored, and schema 5 adds hot-cue data storage. Basic hot-cue GUI set/recall/delete integration exists; deck/session restoration and SQL-backed table searching remain open. Decks start unloaded/paused unless explicit CLI tracks were supplied.

## Location and compatibility

- Windows: `%LOCALAPPDATA%/DrDJPro/library.sqlite3`.
- macOS: `$HOME/Library/Application Support/DrDJPro/library.sqlite3` (path logic only; no macOS acceptance).
- Other platforms: `$XDG_DATA_HOME/DrDJPro/library.sqlite3`, falling back to `$HOME/.local/share/DrDJPro/library.sqlite3` (unqualified).
- `DRDJ_LIBRARY_PATH` may specify an absolute database filename. Relative paths are rejected visibly.
- An existing override ending in `.json` remains supported: that exact file is the legacy source and the database uses the same basename with `.sqlite3`. For other database filenames, the sibling with extension `.json` is the migration source. An arbitrary old JSON filename without `.json` is not guessed or overwritten; choose a distinct database path with the documented sibling convention.

The database uses application ID `0x4452444a` and `PRAGMA user_version=7`. `tracks` is a STRICT table with a positive unique integer ID, Unicode path text and a unique `path_key` computed using the existing platform path-identity rules. `library_meta` records the initial migration source. The separate STRICT `track_metadata` table references track IDs with cascading deletion and stores bounded Unicode tags, nullable millisecond duration, its decoded/header origin, inspection state and errors. Existing track IDs are preserved, and additions receive IDs above the maximum. SQLite schema versions and legacy JSON versions are separate contracts.

The existing 100,000-track and 5,000-path import caps remain safeguards. SQLite rows are bounded/validated on restoration; the legacy reader retains its 32 MiB input limit. SQLite catalogs no longer inherit the old JSON writer's 32 MiB serialized-output limit. These bounds are not scale/performance acceptance.

## One-time JSON migration

A new or transactionally uninitialized database reads the sibling version-1 JSON catalog. If its primary is damaged/missing, a valid JSON `.bak` may be used. A newer JSON version is preserved and rejected, even if an older backup exists. Invalid IDs, duplicates, unsupported/relative paths and oversized JSON are rejected before database creation. JSON and JSON backup bytes are never modified or removed.

Schema creation, the migration-source marker, application/schema versions and imported rows commit in one SQLite transaction. The published JSON version-1 reader still accepts only its original ID/path data; metadata is not written back into JSON. Failure rolls back all of them. An uninitialized file left by interrupted initialization can be retried. Once initialized, SQLite is authoritative: retained JSON is never imported again, even if later changed or corrupted. A missing/damaged SQLite database with an existing SQLite backup restores that backup before considering legacy data; an unrecoverable initialized database is never silently recreated from stale JSON.

All legacy reader and migration tests use temporary profiles; the developer's actual library was not opened or changed by testing.

## Worker, transactions and backup

The existing `library-storage` worker owns its SQLite connection and all database/file operations. The GUI uses the existing bounded command channel; no connection is shared with GUI or audio callbacks. A database OS lock and the matching legacy-profile OS lock exclude both current and JSON-era application writers. The lock files can remain on disk; exclusivity belongs to open OS handles. SQLite still enforces its own transaction locks against other SQLite connections.

The current single-worker architecture uses rollback journaling (`DELETE`) with `synchronous=EXTRA`, foreign keys enabled and trusted schema disabled. WAL is unnecessary for this slice's single connection. A 200 ms SQLite busy timeout prevents an external transaction from indefinitely blocking each lock attempt; failures use the existing visible NOT saved / Retry Save flow.

Regular GUI saves and clean-close flushes use revision-bound deltas: only changed track records are cloned, and crate relationships are included only after crate changes. The worker validates and commits them inside an IMMEDIATE transaction with application/schema and stable ID/path checks. Per-track metadata and bounded cue/grid/loop rows change without reading/rewriting the entire catalog for each cue. Acknowledging a saved revision preserves newer pending edits; failed requests retain their latest records for retry. Full snapshots remain for migration, initialization and optional metadata-backfill writes. Global track deletion/relocation is not introduced by the delta API. Adding or removing crate memberships uses revision-bound per-pair deltas; structural create/rename/delete uses per-crate changes and an ID high-water mark. Rows are now materialized on demand in the existing Slint ListView; catalog-wide in-memory filtering/sorting and paged SQL browsing remain open.

Integrity-checked SQLite online backups use unique synced staged files renamed over `.sqlite3.bak`, never raw live-file copies. Checkpoints run before the first delta and when a previous empty backup can be superseded, on dirty60-second checkpoint opportunities including idle worker timeouts, and on clean close. They no longer run before every cue save. A backup can therefore omit multiple successfully committed changes since its checkpoint; I/O failures can extend its age. SQLite transactions still use synchronous=EXTRA, while backup freshness is a separate guarantee. Failed checkpoint retries back off and emit a distinct warning without completing queued save accounting; Retry Save can retry a checkpoint even when no track delta remains. Clean shutdown flushes the latest pending delta, forces a validated backup and joins the worker; a final failure returns an error exit. GUI-filter/sort/render work still scales with visible catalog size and has no maximum-scale native latency acceptance.

SQLite handles normal interrupted transactions with its journal. On separately damaged primary files, a validated DrDJ/version-compatible SQLite backup can be restored. Damaged primary bytes are first retained in a unique `.damaged.stage-*` file. Foreign or newer-version databases are never replaced by an older backup. If damage coexists with unresolved SQLite journal/WAL sidecars, automatic backup replacement is refused and the originals remain intact. Unrecoverable startup failures visibly enter session-only behavior; subsequent imports cannot overwrite the damaged catalog. Staging files left by abrupt interruption are not treated as committed catalogs.

Missing files retain their ID/path and show MISSING; they are not removed. Loading one reports an error and preserves the installed deck track. Reimporting a restored file at the same path refreshes availability without changing identity. Filesystem watchers and relocation tools remain open.


## Track metadata (introduced in schema 2)

Symphonia, already used for audio, inspects ID3/container tags and header frame/rate information on import/load workers. A missing title falls back to the filename in the table; absent artist/album and unknown duration display as an em dash. File paths remain visible/searchable. Title, artist, album and duration have sort controls; duration sorting is numeric, with unknown durations first in ascending order. IDs remain independent of display order/filtering. A cached path-to-row index avoids scanning the whole catalog for each imported metadata result.

Header-derived durations are conservative estimates displayed with `~`. Loading a track completely replaces that value with decoded PCM length and removes the approximation marker; that origin is persisted. This does not establish musical/gapless duration accuracy across arbitrary files. Tag strings/errors are limited to 512 Unicode scalar values and stripped of control characters during inspection; the reader requests a 512 KiB per-tag metadata limit and skips visuals. Duration storage is bounded to seven days; longer/unknown header durations remain unknown. There is no full PCM decode during ordinary import. An unreadable header retains the path, unknown fields and an explicit error (TYPE column `?`, accessible row description); actual load decoding still decides whether the deck can install a track.

SQLite schemas 1–3 upgrade to 4 in an IMMEDIATE transaction after taking a compatible backup. Schema 1 gains metadata/crate/grid tables; schema 2 keeps metadata and gains crate/grid tables; schema 3 keeps metadata/crates and gains grid storage. A failed upgrade retains the original version and existing IDs/paths/metadata. Existing available tracks without cached inspection results are read on the storage worker, which attempts to persist enrichment before restoration completes. If this optional write fails after a successful read, the readable enriched catalog and worker remain available and Retry Save is offered; fatal read/schema/migration failures retain the preservation/session-only path. Missing files keep unknown or previously cached fields. Cached metadata is reused on subsequent startups, including for now-missing media. Reimporting the same path refreshes its tags without assigning a new ID. There is no tag editing, automatic file-change watcher, artwork, metadata conflict editor or corpus-wide accuracy qualification in this slice.

## Flat crates (schema 3)

`crates` stores stable IDs, printable trimmed names and unique normalized name keys; `crate_tracks` stores unique crate/track pairs with cascading foreign keys and a track lookup index. `library_meta.last_crate_id` is a durable high-water mark, retained even after deleting all crates, so committed crate IDs are not reused after restart. Names contain 1–128 characters after trimming, reject control characters and duplicates under lowercase matching, and reserve All tracks for the built-in view. Limits are 1,024 crates and 1,000,000 memberships; they are safeguards, not scale benchmarks. JSON migration still only reads the original ID/path schema and never writes crate data to retained JSON.

The left navigation displays named crates and unfiltered membership counts plus All tracks. Selecting a crate filters the table by track ID; text search and current sorting apply within that scope, with scoped total/missing counts. Hidden track selections are cleared. New/Rename use a Save/Cancel panel; duplicate or invalid names keep the editor open with a status error. A separate target dropdown supports adding the selected library track to a crate without switching the table filter. Repeated adds are idempotent. Remove only drops the selected membership. Delete requires confirmation, and changing crate navigation cancels a pending confirmation so it cannot act on a stale selection. Deletion removes only that crate/memberships, leaves all library entries/files and playback intact, and returns to All tracks when the active crate is deleted.

File imports capture the active crate when the worker starts. Accepted paths are imported globally and assigned to that captured crate; later filter callbacks cannot redirect membership. Assignment capacity is checked before a bulk set is extended. If membership assignment fails, successfully imported global tracks remain available and the status reports the failure. Direct deck file loading adds a global library entry without implicitly changing crate membership. Active view, target selection and editor state are session-only; startup returns to All tracks.

Crate changes use the background revision-delta save/Retry Save/latest-delta close path; structural create/rename/delete uses per-crate deltas, while membership changes use per-pair deltas. Names, high-water mark, memberships, tracks and metadata commit together. Full online backups and deleting a crate with many members still require work proportional to their data; maximum-scale performance is not qualified. Pure crate logic has no file/audio operations. Nested crates, rule-based smart crates, multi-selection, drag/drop, manual member ordering, external library compatibility and autoplay are not implemented by this slice.

## Transactional manual beatgrids (schema 4)

`track_grids` stores one optional constant-BPM grid per track ID: finite BPM in 40–240 and an integer nanosecond anchor in 0–7 days, with a cascading track foreign key. There is no row for an explicitly removed grid. Original JSON is unchanged and does not receive grid fields. Track/grid/metadata/crate updates commit together, and the previous-good backup includes them. A failed grid write rolls back the whole database transaction. The grid is associated with canonical library path/ID, not a transient filename label or selected table row; it is not an audio-content fingerprint.

Each deck opens an isolated draft of its installed grid, or a new draft anchored at its current playhead if no grid exists. The initial whole-BPM seed/suggestion controls are only active for a new grid; the editor supports decimal points/commas and an explicit suggestion-to-draft button. BPM, Set 1 at playhead, clamped ±10 ms shifts and Clear affect the draft preview only. Existing zoom and explicit waveform seeking remain available. Clear is staged and still needs Save; Set 1 recreates a cleared draft. Invalid BPM cannot replace a valid draft or commit to a deck. Cancel discards it without changing the catalog or active grid. Saving applies the validated local grid and queues background catalog persistence; the footer's Saved/NOT saved/Retry Save state remains the durability indication. Session-only mode says so explicitly.

Visible downbeat labels are numbered relative to the chosen first downbeat (bar 1, marked red in UI code); bars before it can be 0 or negative. Beat positions are recomputed from anchor/index rather than rounded cumulatively. Preview is marked DRAFT; the active-grid flag continues to describe the committed engine state. Editing grid timing does not change playback rate, pitch, samples, mixer gain or play/pause state. It is not Sync, quantization or automatic beat/downbeat detection.

Save checks both the installed track's prepared-source identity and the captured original grid. Reloading/replacing a track discards its old draft; failed/cancelled loading preserves the draft. On normal application loads and library restoration, cached grids are applied to the installed matching track. Raw engine source installation still starts with no grid; the controller is responsible for applying durable library data. An anchor outside a changed file's decoded duration is not applied and is reported for manual repair. Compatible loaded decks of the same canonical track receive the same committed grid, while simultaneous drafts use optimistic conflict detection rather than overwriting one another. A differing loaded counterpart duration can produce an explicit other-deck warning; content-change detection/fingerprinting remains open.

Only committed values are persisted. Drafts, editor state and unsaved invalid text are not restored. Schema-3 upgrade/failure tests preserve metadata/crate membership; restart tests preserve fractional BPM/nanosecond anchors and explicit deletion. Variable-tempo/warp markers, variable meter, musical correctness, native rendering/interaction approval and physical listening are outside this bounded slice.

## Automated acceptance and limits

Tests cover primary/backup JSON migration, byte preservation, Unicode and missing paths, stable IDs/additions, one-time migration, invalid/newer legacy data, transactional schema rollback/retry, partial-write rollback/retry, foreign/newer SQLite preservation, SQLite backup recovery, unrecoverable-data preservation, old/new writer locks and latest-snapshot shutdown flush.

Headless controller tests migrate real MP3/WAV entries, recreate controller/engine/storage, load the same restored ID into A/B paused, retain missing entries and preserve installed audio on error. SQLite writer contention exercises visible failure and Retry Save.

An isolated child process writes a committed catalog, starts an uncommitted transaction with cache spills, and is forcibly terminated. Reopening in the parent restores the committed rows through SQLite's hot journal, releases OS locks and passes `PRAGMA integrity_check`. This is actual process-termination evidence, not physical power-loss qualification.

No visual/native-dialog, physical listening, device-latency, maximum-scale, macOS or Linux acceptance is claimed. Dependency `rusqlite` 0.41.0 uses bundled SQLite and the backup feature, with default optional features disabled; serde/serde_json remain only for legacy migration and tempfile remains test-only.

References: [SQLite pragmas](https://www.sqlite.org/pragma.html), [online backup API](https://www.sqlite.org/backup.html), [rusqlite source](https://github.com/rusqlite/rusqlite).

## Hot-cue storage foundation (2026-10-25)

Schema 5 adds STRICT `track_hot_cues`, keyed by stable track ID and zero-based slot 0–7, with cascading deletion. Each occupied slot stores an integer nanosecond position (0 through seven days), an optional empty Unicode name (at most 128 scalar characters, no controls), and a 24-bit RGB value. Slots are independent; clearing one never compacts or renumbers others. The typed model has private validated fields. Restoration additionally rejects invalid/orphaned/duplicate rows and bounds the total to eight per maximum catalog track count. Names/colors do not modify audio-file tags.

Schema 1–4 upgrades add only missing tables in one transaction, with the existing previous-good backup. Failed schema creation retains the prior version/data. Cue snapshots commit in the same transaction as track metadata, crate membership and grids; explicit removal and track deletion remove cue rows. Library restore/snapshot copies preserve the values, including missing-file entries. Legacy JSON remains ID/path-only and yields empty cue slots.

This is a data-layer foundation, not a usable cue panel: no GUI pads, engine jumps, duration validation against a loaded source, quantization, hardware feedback or session restore is implemented here. Cue positions intentionally remain cached if media changes; the following controller slice must validate against the actual decoded duration before triggering. Storage does not guess duration from approximate header metadata. Full snapshot/backup costs and maximum-size performance remain unqualified.

## Hot-cue deck integration (2026-10-25)

The controller reads and edits the library-owned cue set by the installed source's canonical path. Setting an empty pad snapshots the engine source position and assigns a stable default name/color. With the session-only QUANT option enabled, it instead stores the nearest confirmed manual beat as a canonical source-frame timestamp; grid drafts/missing grids and snapped EOF reject before mutation. Existing recall remains exact, with no grid requirement. Recalling an occupied pad does not dirty/save the library. Deletion clears only the selected slot. Both loaded decks immediately observe shared-path edits through refreshed models; no duplicated per-deck cue store exists. Unchanged cue models are reused. Changes use the existing asynchronous save/footer and final-close flush; applying a cue edit in the GUI is not a durability acknowledgement.

Cue actions respect restore and matching-deck load guards; catalog imports do not block performance controls on loaded decks. Set/recall require a position strictly before actual decoded duration. Out-of-range cached cues are preserved, reported and can be deleted; approximate header duration is never used to clamp them. Absolute engine seeking avoids conversion through the percentage slider and preserves the prior transport/grid/mixer state. Same-track seeking publishes source-frame commands to the installed renderer; this does not establish sample-accurate audible triggering or physical latency. No audio callback code changed.

## Cue name/color edits (2026-10-25)

The GUI editor updates an existing cue through the validated HotCue constructor, preserving its source position and slot. Drafts capture original cue metadata plus the installed prepared-source identity. Save rejects a changed/deleted cue or replaced source; Cancel has no persistence side effect. Changes use the existing worker/snapshot transaction and footer durability feedback. Schema 5 already stores these values, so no migration/dependency was added. Cached positions outside a changed media file remain repairable metadata; they are not clamped or rendered as valid markers. Unicode names and RGB colors survive fresh controller/storage restart.

## Saved-loop storage foundation (2026-10-25)

Schema 6 adds STRICT track_saved_loops(track_id, slot, start_ns, end_ns, name), with a composite primary key and cascading track deletion. Eight fixed zero-based slots per track store optional named regions; clearing a slot never moves others. Private typed fields validate 0 <= In < Out <= seven days and Unicode names up to 128 scalar characters without control characters. Integer nanoseconds avoid persistence rounding. Restoration bounds total rows to eight per maximum track count and rejects invalid, duplicate and orphaned rows even when table constraints were bypassed.

Schemas 1–5 upgrade transactionally with the existing compatible backup; failure retains the old version/data. Loop rows commit in the same save transaction as metadata, hot cues, grids and crates. Retry/backup/normal-close worker behavior remains unchanged. Library restore/snapshot copies preserve loop metadata even for missing files; legacy JSON remains ID/path only and supplies empty slots. No media tags are modified.

Saved loop metadata does not activate playback or restore a deck session. It permits positive nanosecond regions without knowing the current sample rate or duration; the subsequent recall path must validate loaded duration and a nonempty frame-aligned interval, retaining cached data for repair if media changed. No auto-clamping, content fingerprinting, external loop-format compatibility or maximum-scale performance qualification is claimed. GUI saved-slot editing/recall/deletion is the next separate slice.

## Saved-loop GUI integration (2026-10-25)

Save snapshots a loaded deck's valid In/Out into an empty selected slot with its entered/default name. Occupied targets fail without mutation; Delete is explicit and never changes active engine playback. Same canonical-path decks share library data immediately, with unchanged models reused. Changes use the existing queued SQLite transaction and footer/final-close durability flow; Recall does not dirty the catalog. Name input resets after successful source replacement. The existing schema 6 needs no migration for these controls.

Recall validates the entire interval against loaded duration and complete sample frames before changing any deck state. Out-at-EOF snapshots are clamped to decoded duration to avoid a one-nanosecond round-trip overrun; interval conversion preserves exact frame endpoints where representable. Invalid cached data remains intact for explicit deletion/repair. Successful recall exits an old active loop at its current phase, installs the new inactive boundaries, and preserves Play/Pause, source position, grid and mixer. LOOP separately toggles activation, preserving position inside the interval and starting at In when outside; RELOOP explicitly activates/restarts at In. Both preserve Play/Pause. No automatic activation/session restoration, overwrite, renaming editor, external format compatibility or physical timing guarantee is implied.


## Incremental crate memberships (2026-10-27)

Library coalesces each changed (crate ID, track ID) to its latest present/absent state and revision. Successful save acknowledgements discard only changes at or below the saved revision, preserving newer edits to the same pair. Import batches record only actual additions; duplicate additions do not dirty the catalog. At the initial membership checkpoint structural changes still took a full crate snapshot; the subsequent structural delta checkpoint below removes this dependency.

The storage worker validates each referenced ID and applies membership INSERT or DELETE operations within the same IMMEDIATE transaction as track changes. Failure rolls the transaction back; retry/close and periodic checkpoint semantics remain unchanged. Existing database schema is unchanged. A focused 2,000-track fixture with two large crates proves two membership changes write exactly two SQLite rows, preserve unrelated membership and survive a restart. Injected write failure rolls back the first operation. This is bounded row-write evidence, not a benchmark or maximum-scale latency claim; scheduled backup inspections may still scale with the entire catalog.


## Incremental crate structure (2026-10-27)

Create, rename and delete now record changed crate IDs with their current name or deletion state and revision, plus the monotonic ID high-water mark. Acknowledgement preserves later changes, including deleting a crate whose creation is still being saved. Worker transactions validate IDs and names, delete only requested crates (with their membership cascade), update only changed crates, and then apply member deltas. Temporary NUL-prefixed name keys are confined to the transaction, allowing multiple valid renames to exchange names without a transient UNIQUE collision; failed writes roll back keys, names and memberships together. No schema migration is needed.

A 1,000-track fixture with 1,000 and 500 memberships checks name swapping, bounded row writes and preserved members with a trigger forbidding membership deletion; an injected failure tests rollback and restart. A separate test covers in-flight create/delete/recreate, combined membership and ID high-water across restart. Deleting a crate necessarily deletes its members. Whole-catalog initialization/backups, filtering/sorting and large-view virtualization remain separate scaling work; no maximum-scale timing guarantee is made.


## Lazy library rows (2026-10-27)

The published Slint list model stores sorted IDs and retrieves each LibraryRow only when requested. A track-ID lookup avoids a linear search for each row; loading a replacement catalog invalidates old models through a generation check. The model holds weak references to controller-owned data, and transient mutable-borrow contention returns no row rather than panicking. Normal library publication replaces the model after changes. No database schema change, SQL paging, lazy track import or background sorting is introduced.

The 20,000-track headless viewport requested two rows. A separate preparation-only allocation comparison after obtaining an already sorted visible list measured1 allocation for IDs versus200,001 for materializing all row objects. These figures exclude catalog filtering/sorting, ID-index creation and GUI rendering, and do not establish native scrolling or latency on a particular device. The current filter/sort and ID-vector rebuild remain proportional to the catalog.


## Reusing unchanged in-memory views (2026-10-27)

The in-memory Library caches sorted, filtered stable track indices and invalidates them on changed query/sort/scope, track mutation and membership mutation. Repeating the same normalized query retains the cache. Selection, metadata and crate mutation tests confirm the next read rebuilds when needed. The lazy GUI row model continues to fetch live row values by ID. Cold filtering/sorting is still full-catalog work; cached reads still walk the selected result and create a reference vector, and library publication still builds an ID vector. Cache memory is proportional to visible entries. New track mutations conservatively invalidate the cache even when they only change cue/grid data. SQLite paging, large cold-search optimization and native latency remain open.


## Prepared text for new views (2026-10-27)

Track search maintains lowercased title, artist, album, filename and path alongside each track. Insertion and restoration initialize them; metadata changes refresh them. Filtering uses the same substring semantics and sorting compares the same normalized values, optional duration and stable ID as before without allocating a String sort key per track for each cold view. The test suite compares all six fields and both directions against the previous expressions, including Unicode, missing metadata, crate filtering and restore.

This trades five per-track String fields and their metadata-update work for fewer allocations when building a cold view. A local 10,000-track fixture reported16 cold and1 cached allocations versus10016 and1 before this step; the measurement excludes insertion/normalization, rendering, and any comparison of overall memory or wall time. Search still scans, sorting still sorts the in-memory catalog, and SQL paging/indexed search plus native latency remain open.


## ID-indexed selection (2026-10-27)

Selection now resolves stable IDs through the in-memory ID index and applies the same query and active-crate predicate as view construction. Existing selection is revalidated directly when the query is set; the selected file path is obtained by ID. This avoids a whole-track scan or building/sorting the visible list for these actions, while preserving selection of hidden tracks or nonexistent IDs as invalid and preserving the old selected-path semantics after metadata updates. Finding an active crate scans bounded crate entries and testing a query still scans that track's fields. Next/previous navigation, cold full-text filtering/sorting, ordered-ID publication, SQLite paging and native performance remain separate work.

Schema 7 adds `track_grids.beats_per_bar` (integer 1–16, default 4). Upgrades preserve old grids as four quarter beats per bar in the existing backup/transaction flow. The value is quarter-beat count, not a general numerator/denominator time signature or a within-track meter map.

## Quantize preference persistence (2026-10-29)

The existing library_meta table now optionally contains quantize_preferences_v1, a strictly validated JSON object with version 1, global enabled state and exactly two deck records (cue snap, scheduled trigger, Auto Loop snap and step index 0-5). No SQL schema migration is needed; existing databases without the key keep master On, deck options Off and one-beat steps. Preference reads are capped at 1024 bytes in SQL with length(CAST(value AS BLOB)), including embedded-NUL cases. Invalid JSON, unknown versions/fields, missing members and invalid steps produce a preference warning/defaults while keeping the library available. The malformed original row is retained until an actual preference change is saved.

All database operations stay in the existing storage worker. Optional preferences and a catalog delta share one transaction, so a preference write failure rolls back catalog changes too. Preferences-only saves do not traverse/rewrite all tracks; they use the existing bounded command queue, acknowledgement/retry and checkpoint machinery. The SQLite backup includes the preference key. Complete catalog saves preserve it. This is per-catalog-path application state, not a track property and not portable JSON-catalog export.

The controller compares observed, acknowledged and inflight immutable preference snapshots. Changes made before the earlier save is acknowledged remain pending; success acknowledges only the captured snapshot. Close flushes the latest settings even without another GUI tick, including a revert to the previously acknowledged value while a different value is inflight. Closing before restore completes never replaces saved settings with UI defaults. Preference controls are temporarily disabled during restore. Corrupt preference warnings do not force a catalog reset or an automatic default write. Transport/playback, pending cue requests, active Sync/nudge ownership, Keylock jobs and loaded-track identities are not persisted by this model.

## Source diagnostic backfill (2026-10-29)

Legacy no-reader and unsupported-WAVE metadata errors are now eligible for worker backfill alongside the previous ID3 errors. Empty/tag-limited, unrecognized and invalid-WAVE failures receive stable new messages so a permanent no-reader failure does not cause an unchanged expensive parser retry at every restart. Successful MPEG-WAVE warnings remain cached. The existing availability guard and before/after comparison still prevent writes for unavailable/unchanged entries. SQLite restart regressions cover empty files and permanent nonempty junk, including a trigger rejecting an unexpected second backfill. No schema migration is required.

## AppleDouble import filtering (2026-10-29)

Import workers reject AppleDouble magic 0x00051607 with version 0x00010000 or 0x00020000 before audio metadata probing. Only eight header bytes are read; a filename starting with ._ alone is never excluded. Rejected entries use the existing import rejection count and do not enter the catalog or metadata batch. Short headers, unknown versions and read failures retain the existing audio inspection/error path. Existing saved entries are not removed, and no file is edited. This check is deliberately separate from the extension-only supported() predicate used by catalog validation.

## Guarded output route profiles (2026-10-29)

The existing library_meta key audio_output_routes_v1 optionally holds version 1 output profiles: at most 32 entries, each with backend, exact device display name, actual channel count and stereo pair. This is a name/format binding, not a hardware serial/endpoint ID. At stream startup a key is enabled only if that device name occurs exactly once among the current backend's output devices. Profiles do not transfer across different names, backends or channel counts. Identically named replacement hardware across separate sessions cannot be distinguished; stable hardware IDs and device selection remain open.

The worker validates strict JSON and byte-bounds reads at 64 KiB in SQL, including embedded-NUL cases. Matching existing profiles remain writable at capacity. New devices with a full table, unavailable/ambiguous identities and corrupt/future profile data use session-only routing with a persistent toolbar indicator; malformed original rows are not rewritten and unrelated catalog/Quantize saves still work. Output profile updates merge with other entries and share the catalog/Quantize transaction, acknowledgements, retry and final shutdown flush. Newer choices and reverts before an earlier save acknowledgement are retained. A corrupt/future table rejects direct profile writes rather than discarding unknown data; the controller suppresses such writes while allowing session routing and other saves.

Output opening now resolves the default device explicitly and permits format fallback only on that same device. If it cannot open, it reports failure rather than silently changing output devices and applying a route to the wrong destination. Actual channel count after format fallback participates in the profile key. No structural schema migration, new dependency or per-sample profile lookup was added.
